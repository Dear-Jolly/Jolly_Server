# 커밋 메시지 규칙

## 형식

```
{type}: {무엇을 했는지 한 줄}
```

제목 한 줄이 기본이다. 본문은 없어도 된다.

```
feat: 편지 상세 조회 API 구현
fix: 편지 목록 정렬이 같은 날짜에서 뒤집히는 문제 수정
build: 테스트에서 Colima Docker 소켓을 자동으로 찾도록 변경
```

| type | 쓰는 때 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조 변경 |
| `test` | 테스트만 추가·수정 |
| `docs` | 문서만 변경 |
| `build` | 빌드 설정·의존성 |
| `chore` | 그 외 잡일 |

## 제목 쓰는 법

- **무엇을 했는지**를 한국어 평서형으로 쓴다. `구현`, `수정`, `추가`, `제거`, `변경`.
- 파일명·클래스명을 나열하지 않는다. `git show` 로 보면 되는 정보다.
- 한 줄에 안 들어가면 커밋이 너무 큰 것이다. 나눈다.

## 본문은 기본적으로 쓰지 않는다

**꼭 필요한 경우에만** 쓴다. 판단 기준은 — **코드만 봐서는 이유를 알 수 없고, 나중에 누가 되돌릴 위험이 있는가?**

| 본문을 쓴다 | 본문을 쓰지 않는다 |
|---|---|
| 명세와 다르게 구현했고 그 이유가 코드에 안 드러날 때 | 변경 내용을 다시 풀어 쓰는 것 |
| 눈에 안 보이는 부작용·마이그레이션 절차가 있을 때 | 파일 목록·클래스 목록 |
| 되돌리기 어려운 결정을 했을 때 | "테스트 추가함" 같은 당연한 말 |

본문을 쓴다면 두세 줄이면 충분하다.

```
feat: 편지 상세 조회 API 구현

읽음 처리는 피드백이 완료된 편지에만 건다. 완료 전 조회로 열람 처리하면
피드백이 도착한 뒤 미열람 표시가 뜨지 않는다.
```

## 커밋 범위

- **한 커밋에는 한 가지 일만 담는다.** 기능과 빌드 설정 변경이 섞이면 나눈다.
- 워킹트리에 내 작업이 아닌 변경이 섞여 있으면 **그 파일은 빼거나, 내 변경만 골라 스테이징**한다.
- 커밋 전에 **빌드와 테스트가 통과하는지 확인**한다. 깨진 상태를 커밋하지 않는다.

## 금지

- **AI·도구 관련 문구를 남기지 않는다.** `Co-Authored-By` 트레일러, `Generated with ...`, 어시스턴트 이름 언급 전부 해당한다.
- 이모지를 넣지 않는다.
- `WIP`, `수정`, `ㅇㅇ` 같은 내용 없는 제목을 쓰지 않는다.
