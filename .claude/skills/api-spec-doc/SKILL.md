# API명세.md 작성 규칙

## 이 문서의 목적

`docs/API명세.md` 는 **앱(프론트)과 서버가 주고받는 요청/응답 계약의 정본**이다.
독자는 프론트 개발자다. **프론트가 화면을 만들고 통신 코드를 짜는 데 필요한 것만** 적는다.

판단 기준 하나로 정리하면 — **"앱의 동작이 달라지는가?"**
달라지면 적고, 안 달라지면 뺀다.

## 절대 적지 않는 것

| 분류 | 예시 |
|---|---|
| 설계 배경·이유 | "`jti` 를 넣는 이유는…", "버전을 DB 가 아니라 설정에 두는 이유는…" |
| 서버 내부 구현 | JPA cascade, 트랜잭션 경계, 인증 필터 동작 순서, 패키지 위치, 환경변수명 |
| 히스토리·범위 | "MVP 는 …하지 않는다", "재동의 유도는 MVP 밖", "추후 확장 시…" |
| 서버만 아는 사정 | DB 컬럼명, URL 조립 방식, 배치 잡, 내부 상태값 |
| 디자인 문구 인용 | *"편지는 잘 보관해 둘게요"* 같은 카피 |

에러 코드가 **왜** 그렇게 나뉘었는지가 아니라, **어떤 상황에 어떤 코드가 오는지**만 적는다.

## 용어

서버 용어가 아니라 **프론트가 바로 이해하는 비즈니스 용어**를 쓴다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| Refresh Token 회전(rotate) | 이전 값으로는 재발급할 수 없다 |
| 단일 세션 정책 | 기기 1대만 유지된다 |
| non-null 보장 | 항상 값이 있다 |
| IANA 타임존 ID | 기기 타임존 ID |
| 애그리거트 · 영속성 컨텍스트 | (쓰지 않는다) |

## 문서 구조

```
# Dear Jolly — API 명세서 (MVP)
(메타 정보 표: 최종 갱신 · Base URL · 인증 · Content-Type · 날짜 포맷)

# 1. 엔드포인트 목록
# 2. API 명세
# 3. Enum 정의
# 4. Error Code 정의
# 5. 그 외 규약 정의
```

- 최상위 제목은 `#`, API 항목과 하위 규약은 `##`, API 내부 구획은 `###` 이다.
- 문서 맨 앞에 목적을 설명하는 인용문(`>`)을 두지 않는다. 표부터 시작한다.

## 1. 엔드포인트 목록

| # | Method | 엔드포인트 | 설명 | 인증 | 온보딩 | 구현 |

- `#` 은 API 명세 항목으로 가는 **바로가기 링크**다.
- 서버 구현 위치(패키지) 같은 열은 두지 않는다.
- 표 아래에 열의 의미를 불릿으로 짧게 정의한다.

## 2. API 명세 — 항목 형식

```markdown
## 10) POST /api/v1/letters ✅

### [설명]

- (전부 불릿)

### [스펙]

**Endpoint**
**Authorization 헤더**
**Path Variable** / **Request Parameter** / **Query Parameter** / **Body**
**검증 규칙** (있으면 표)

### [성공 Response 201]

### [실패 Error Response]
```

### 제목

- 형식은 `## {번호}) {METHOD} {경로} {구현마커}` 다.
- **구현 마커는 제목 끝에 붙인다.** ✅ 호출 가능(통합 테스트까지 있음) / ❌ 명세만 확정, 개발 전.
- `> 구현 완료 ✅` 같은 인용문 블록을 따로 두지 않는다.

### [설명] — 전부 불릿

- **평문 단락을 쓰지 않는다. 모든 줄이 `-` 로 시작한다.**
- 표(`| … |`), 인용문(`>`), `**소제목**` + 하위 목록 구조를 두지 않는다.
  기존에 그런 블록이 있으면 **불릿 한 줄씩으로 풀어서 흡수**한다.
- 앱 분기, 렌더링 규칙, 주의사항도 전부 불릿 한 줄이다.
- 첫 불릿은 이 API 가 무엇을 하는지 한 줄로 쓴다.
- 앱이 반드시 지켜야 하는 조건은 **굵게** 표시한다.

```markdown
### [설명]

- 카카오가 호출하는 주소다. **앱이 직접 호출하지 않는다.**
- 앱은 딥링크로 받은 값으로 진입 화면을 정한다. **`termsAgreed == false` → 약관동의 화면**,
  **`termsAgreed == true` 이고 `nicknameRegistered == false` → 닉네임 화면**, **둘 다 `true` → 홈**이다.
- **토큰이 URL 에 실려 오므로**, 딥링크를 받은 즉시 보안 저장소로 옮긴다.
```

### [스펙]

- `**소제목**` + 코드블록/불릿으로 쓴다.
- **표 아래에 떠도는 평문 단락을 두지 않는다.** 설명이 필요하면 `[설명]` 불릿으로 올린다.
- 검증 규칙이 순서를 타면 표에 **순서 열**을 둔다.

### 필드 표기

- 형식은 `- [필수] {필드명} ({타입}): {설명}` 이며, 선택 필드는 `[선택]` 이다.
- 중첩 필드는 4칸 들여쓰기로 계층을 표현한다.
- `null` 이 되는 조건은 그 필드 줄에 **굵게** 적는다.
- 예시 JSON 을 먼저 두고 그 아래에 필드 목록을 둔다.

### Response 섹션

- 성공은 `### [성공 Response {상태코드}]`, 실패는 `### [실패 Error Response]` 다.
- 같은 API 가 상황에 따라 다른 성공 코드를 내면 섹션을 나누고 제목에 사유를 붙인다.
  (예: `### [성공 Response 200 — 중복 전달]`)
- 실패 섹션은 **에러 응답 예시 JSON + 코드 표**로 구성한다.
- 모든 API 에서 공통으로 발생하는 코드(`AUTH_005` · `AUTH_006` · `AUTH_007`, `COMMON_*`)는
  개별 API 표에 반복하지 않는다.

## 목차 앵커 규칙

제목 끝에 이모지가 붙으므로 **앵커 끝에 하이픈이 하나 더 붙는다.**

| 제목 | 앵커 |
|---|---|
| `## 4) POST /api/v1/auth/reissue ✅` | `#4-post-apiv1authreissue-` |
| `## 11) GET /api/v1/letters/{letterId} ❌` | `#11-get-apiv1lettersletterid-` |

규칙은 — 소문자로 바꾸고, 문장부호(`)` `/` `.` `{` `}`)와 이모지를 제거하고, 공백을 `-` 로 바꾼다.
**API 항목을 추가·삭제·개명하면 엔드포인트 목록과 본문 상호 참조 링크를 함께 고친다.**

## 갱신 시점

- **API 를 추가하거나 요청/응답을 바꿨다면 이 문서를 함께 고친다.**
- **구현이 끝나면 마커를 ❌ → ✅ 로 바꾼다.** 기준은 컨트롤러·서비스·통합 테스트가 모두 있는 상태다.
  엔드포인트 목록의 `구현` 열과 API 제목 **두 곳을 함께** 바꾼다.
- 새 에러 코드를 만들었으면 `4. Error Code 정의` 의 도메인별 표에 추가하고,
  해당 API 의 실패 표에도 넣는다.
- 새 enum 값이 API 로 나가면 `3. Enum 정의` 에 추가한다.
- 상단 메타 표의 `최종 갱신` 날짜를 고친다.

## 자가 점검

- [ ] `[스펙]` 안에 떠도는 평문 단락이 없는가
- [ ] 구현 마커가 제목 끝에 있고, 엔드포인트 목록과 값이 같은가
- [ ] 목차·상호 참조 링크가 실제 제목과 맞는가
- [ ] 서버 내부 구현·설계 배경·MVP 히스토리가 섞이지 않았는가
- [ ] 모든 필드에 `[필수]`/`[선택]` 과 타입이 붙어 있는가
- [ ] 새 에러 코드·enum 이 `4. Error Code 정의`·`3. Enum 정의` 에 반영됐는가
