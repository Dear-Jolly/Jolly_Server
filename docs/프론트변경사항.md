# 프론트엔드 변경 사항 — 2026-08-30

2026-08-23 마지막 배포분과 2026-08-30 현재 코드를 비교해, **앱 동작이 달라지는 것만** 정리했습니다.

## 1. 요약

- API 엔드포인트, 요청 형식, 정상 응답의 필드명·타입은 변경되지 않았습니다.
- 편지 상태 `Status` 에 **`FEEDBACK_FAILED` 값이 추가**되었습니다. API 오류가 아니라 정상 `200` 응답의 `status` 값입니다.
- **피드백 생성이 한 번이라도 실패하면 그 즉시 `FEEDBACK_FAILED` 와 실패 우표(`fail`)로 내려갑니다.**
- **`FEEDBACK_FAILED` 는 최종 상태가 아닙니다.** 서버가 뒤에서 재시도를 이어가므로, 다시 조회하면 `FEEDBACK_COMPLETED` 로 바뀌어 있을 수 있습니다.
- 우표 이미지에 `fail.png` 가 추가되었습니다. 기존 `soon.png` 와 마찬가지로 서버가 상태에 따라 붙입니다.
- 모든 `/api/**` 요청에 IP 기준 분당 120회 제한이 추가되었습니다.
- `POST /api/v1/letters` 에는 사용자 기준 분당 5회 제한이 추가되었습니다. 초과 시 `429` / `COMMON_004` 입니다.
- 모든 응답에 `X-Request-Id` 헤더가 내려옵니다. 장애 문의 시 이 값을 함께 전달하면 서버 로그를 바로 찾을 수 있습니다.
- 문장부호만 달라진 교정 조각은 `MODIFIED` 가 아니라 `UNCHANGED` 로 내려갑니다.

## 2. 편지 상태와 우표 정책 (가장 큰 변경)

### 2-1. 규칙

| 상황 | 응답 `status` | 응답 `stampImage` |
| --- | --- | --- |
| 아직 한 번도 실패하지 않은 처리 중 | `SUBMITTED` · `FEEDBACK_IN_PROGRESS` | `soon`(준비 중) 우표 |
| **한 번이라도 실패한 뒤** | `FEEDBACK_FAILED` | `fail`(실패) 우표 |
| 피드백 완료 | `FEEDBACK_COMPLETED` | AI 가 편지에 맞춰 고른 우표 |

- 첫 실패 전까지는 무조건 `soon` 입니다.
- 한 번이라도 실패하면 그 순간부터 `fail` 로 확정됩니다. 서버가 내부적으로 재시도 중이어도 앱에는 계속 `FEEDBACK_FAILED` 만 내려갑니다.
- 내부 재시도가 성공하면 그때 `FEEDBACK_COMPLETED` 와 편지에 맞는 우표로 **한 번에** 바뀝니다.
- 준비 중 ↔ 실패를 오가는 응답은 존재하지 않습니다. 앱이 안내 문구를 번복할 일이 없습니다.

### 2-2. 앱 처리 규칙

`FEEDBACK_FAILED` 카드·상세는 다음과 같이 처리합니다.

- 준비 중 애니메이션을 종료하고 실패 안내를 표시합니다.
- 상세 화면 진입을 막습니다.
- `isRead == false` 여도 미열람 빨간 점을 표시하지 않습니다.
- `stampImage` 는 상태로 직접 조합하지 않고 응답 URL 을 그대로 사용합니다.
- **화면 재진입·새로고침 때 다시 조회합니다.** 서버 재시도가 성공하면 완료 상태로 바뀌어 있을 수 있습니다.

기존 안내에서 바뀐 부분은 마지막 항목입니다. 이전 문서에는 `FEEDBACK_FAILED` 에서 자동 새로고침을 중단하라고 적었으나, 지금은 **완료로 바뀔 수 있으므로 재조회 대상**입니다. 상태 변화를 알리는 별도 폴링 API 는 여전히 없습니다.

### 2-3. `GET /api/v1/letters`

```json
{
    "letters": [
        {
            "letterId": 15,
            "date": "2026-08-30",
            "summary": "I wrote a letter today...",
            "status": "FEEDBACK_FAILED",
            "isRead": false,
            "stampImage": "https://{host}/dear-jolly-stamps/stamp/fail.png"
        }
    ],
    "hasNext": false
}
```

### 2-4. `GET /api/v1/letters/{letterId}`

```json
{
    "letterId": 15,
    "date": "2026-08-30",
    "originalContent": "I wrote a letter today...",
    "status": "FEEDBACK_FAILED",
    "stampImage": "https://{host}/dear-jolly-stamps/stamp/fail.png",
    "feedback": null
}
```

- HTTP 상태는 오류가 아닌 `200 OK` 입니다.
- `feedback` 은 `FEEDBACK_COMPLETED` 에서만 값이 있습니다. `SUBMITTED` · `FEEDBACK_IN_PROGRESS` · `FEEDBACK_FAILED` 에서는 `null` 입니다.

## 3. 요청 제한 추가

- 모든 `/api/**` 요청은 클라이언트 IP 기준 분당 120회까지 허용됩니다.
- `POST /api/v1/letters` 는 인증된 사용자 기준 분당 5회까지 허용됩니다. 편지 작성에는 두 제한이 모두 적용됩니다.
- 제한 횟수는 고정된 1분 단위로 계산됩니다.
- 둘 중 하나라도 초과하면 `429 Too Many Requests` 와 `COMMON_004` 를 반환합니다.
- 앱은 `429` 를 받으면 즉시 반복 요청하지 말고 잠시 기다린 뒤 다시 시도합니다.

```json
{
    "status": 429,
    "code": "COMMON_004",
    "message": "요청이 너무 많습니다. 잠시 후 다시 시도해주세요."
}
```

| 적용 대상 | 식별 기준 | 분당 허용 횟수 | 초과 응답 |
| --- | --- | ---: | --- |
| 모든 `/api/**` 요청 | 클라이언트 IP | 120회 | `429` / `COMMON_004` |
| `POST /api/v1/letters` | 인증된 사용자 | 5회 | `429` / `COMMON_004` |

## 4. `X-Request-Id` 응답 헤더

- 모든 응답에 `X-Request-Id` 헤더가 포함됩니다. 요청 한 건마다 서버가 새로 발급하는 값입니다.
- 앱이 이 헤더를 보낼 필요는 없습니다. 보내더라도 서버는 자체 발급 값을 사용합니다.
- 오류를 제보할 때 응답에서 받은 값을 함께 전달하면 해당 요청의 서버 로그를 바로 찾을 수 있습니다.

## 5. 교정 구간의 문장부호 처리

- 단어·표현은 같고 **쉼표·마침표 등 문장부호만 다른 조각**은 `type` 이 `MODIFIED` 가 아니라 `UNCHANGED` 로 내려갑니다.
- `correctedText` 에는 교정문의 문장부호가 그대로 들어 있으므로, 이어붙여 그린 결과 문장은 이전과 동일합니다.
- 앱이 바꿀 것은 없고, 문장부호 차이 때문에 빨간 취소선이 과하게 찍히던 화면이 정리됩니다.

## 6. 최종 enum 종류 (`Status`)

| 값 | 의미 | 프론트 처리 |
| --- | --- | --- |
| `SUBMITTED` | 피드백 작업 대기 (실패 이력 없음) | 준비 중 표시, 상세 진입 차단, 재조회 |
| `FEEDBACK_IN_PROGRESS` | 피드백 생성 중 (실패 이력 없음) | 준비 중 표시, 상세 진입 차단, 재조회 |
| `FEEDBACK_COMPLETED` | 피드백 생성 완료 | 완료 우표 표시, 상세 진입 허용 |
| `FEEDBACK_FAILED` | 한 번 이상 실패 | 실패 우표·실패 안내, 상세 진입 차단, 재조회 |

권장 분기:

```text
SUBMITTED | FEEDBACK_IN_PROGRESS -> 준비 중 (soon 우표)
FEEDBACK_COMPLETED               -> 완료   (편지에 맞는 우표)
FEEDBACK_FAILED                  -> 실패   (fail 우표, 다음 조회에서 완료로 바뀔 수 있음)
```
