# Dear Jolly 로그 체계

| 항목 | 내용 |
| --- | --- |
| 최종 갱신 | 2026-08-30 |
| 형식 | 단일 행 `event_name key=value` |
| 요청 식별자 | 서버가 발급한 UUID `requestId` |
| 사용자 식별 | `userId`, `nickname` |
| 시간대 | `Asia/Seoul` |

## 1. 목적

Dear Jolly의 로그는 서버 클래스나 메서드 실행 여부보다 다음 비즈니스 질문에 답하는 것을 우선한다.

- 어떤 사용자가 어떤 API를 호출했는가?
- 요청은 성공했는가, 거절됐는가, 서버 오류가 발생했는가?
- 사용자가 작성한 편지는 신규로 저장됐는가, 중복 요청으로 처리됐는가?
- 피드백 작업은 어느 편지에서 몇 번째 시도를 수행하고 있는가?
- OpenAI 응답은 성공했는가? 실패했다면 실제 원인은 무엇인가?
- 재시도 또는 보완 복구는 언제, 왜 실행됐는가?
- 최종적으로 편지가 `FEEDBACK_COMPLETED`와 `FEEDBACK_FAILED` 중 어느 상태가 됐는가?

## 2. 기본 원칙

### 단일 행 구조화 로그

모든 비즈니스 로그는 다음 형식을 사용한다.

```text
event_name key1=value1 key2=value2 key3=value3
```

고정된 이벤트 이름과 필드명을 사용하므로 `requestId`, `userId`, `letterId`로 검색하거나 로그 수집 도구에서 집계할 수 있다.

### 요청과 비동기 작업 구분

- HTTP 요청은 `requestId`로 시작과 완료를 연결한다.
- 편지 피드백은 요청이 끝난 뒤 비동기로 실행되므로 `letterId`를 기본 추적 키로 사용한다.
- 최초 피드백 작업과 일반 재시도에는 원래 요청의 MDC 문맥을 전달한다.
- 스케줄러가 독립적으로 발견한 보완 복구는 원래 요청 문맥이 없을 수 있으므로 `userId`, `nickname`, `letterId`를 로그 본문에 직접 기록한다.

### 민감정보 금지

다음 값은 로그에 기록하지 않는다.

- JWT access token과 refresh token
- 관리자 비밀번호와 OpenAI API 키
- OAuth 인가 코드와 Apple `id_token`
- 편지 원문과 OpenAI가 생성한 전체 교정문
- 요청 body 전체

편지 원문 대신 문자 수인 `contentLength`만 기록한다. 예외 메시지와 문자열 필드는 줄바꿈·탭을 제거하고 최대 500자로 제한해 로그 변조와 과도한 출력을 막는다.

## 3. 공통 MDC 필드

애플리케이션 로그 레벨 영역에는 다음 MDC 필드가 자동으로 붙는다.

| 필드 | 설명 | 값이 없는 경우 |
| --- | --- | --- |
| `requestId` | HTTP 요청마다 서버가 발급한 UUID | `none` |
| `userId` | 인증된 사용자 ID | `anonymous` 또는 `none` |
| `nickname` | 인증된 사용자의 현재 닉네임 | `anonymous` 또는 `none` |

응답 헤더 `X-Request-Id`에도 같은 `requestId`가 들어간다. 프론트나 운영자가 장애를 제보할 때 이 값을 전달하면 요청 전체를 바로 찾을 수 있다.

## 4. 로그 레벨 기준

| 레벨 | 사용 기준 | 예시 |
| --- | --- | --- |
| `INFO` | 정상적인 비즈니스 흐름 | 요청 성공, 편지 저장, 피드백 완료 |
| `WARN` | 예상 가능한 거절 또는 복구 가능한 문제 | 400·401·403·404·429, AI 재시도, 보완 복구 |
| `ERROR` | 자동 복구가 끝난 실패 또는 서버 장애 | 500, 피드백 최종 실패, 재시도 예약 실패 |

예상 가능한 `BusinessException`은 서버 장애가 아니므로 `WARN`으로 기록한다. 예상하지 못한 `RuntimeException`은 스택 트레이스와 함께 `ERROR`로 기록한다.

## 5. HTTP 요청 이벤트

### `business_request_started`

Spring MVC가 처리할 `/api/**` 요청이 시작될 때 기록한다.

| 필드 | 설명 |
| --- | --- |
| `method` | HTTP 메서드 |
| `path` | 쿼리 문자열을 제외한 요청 경로 |
| `operation` | 처리할 Controller 메서드 |
| `clientIp` | `X-Forwarded-For`의 첫 IP 또는 직접 접속 IP |

```text
business_request_started method=POST path=/api/v1/letters operation=LetterController.createLetter clientIp=203.0.113.10
```

### `business_request_completed`

요청 처리가 끝났을 때 성공과 실패 모두 기록한다.

| 필드 | 설명 |
| --- | --- |
| `method` | HTTP 메서드 |
| `path` | 요청 경로 |
| `status` | 최종 HTTP 상태 코드 |
| `elapsedMs` | 서버 처리 시간 |
| `exception` | MVC까지 전달된 예외 종류. 없으면 `none` |

상태 코드가 400 이상이면 `WARN`, 500 이상이면 `ERROR`다.

## 6. 요청 거절과 서버 오류 이벤트

| 이벤트 | 레벨 | 설명 |
| --- | :---: | --- |
| `business_request_rejected` | WARN | ErrorCode로 정의된 비즈니스 요청 거절 |
| `request_validation_failed` | WARN | Request body 필드 검증 실패 |
| `request_parameter_validation_failed` | WARN | 메서드 파라미터 제약 위반 |
| `request_parameter_missing` | WARN | 필수 파라미터 누락 |
| `request_parameter_type_mismatch` | WARN | 파라미터 타입 불일치 |
| `request_json_parse_failed` | WARN | JSON 형식 오류 |
| `request_method_not_allowed` | WARN | 지원하지 않는 HTTP 메서드 |
| `request_path_not_found` | WARN | 존재하지 않는 경로 |
| `unexpected_request_failure` | ERROR | 처리하지 못한 런타임 오류 |

`business_request_rejected`에는 `code`, HTTP `status`, 사용자에게 반환할 `message`가 포함된다.

## 7. 편지 이벤트

| 이벤트 | 레벨 | 설명 | 주요 필드 |
| --- | :---: | --- | --- |
| `letter_created` | INFO | 새 편지 저장 완료 | `userId`, `letterId`, `letterDate`, `timeZone`, `contentLength`, `status` |
| `letter_submission_deduplicated` | INFO | 60초 이내 동일 편지를 기존 편지로 처리 | `userId`, `letterId`, `contentLength`, `status` |
| `letter_detail_viewed` | INFO | 편지 상세 조회 | `userId`, `letterId`, `status`, `markedAsRead` |
| `letter_list_viewed` | INFO | 편지 목록 조회 | `userId`, `page`, `size`, `sort`, `resultCount`, `hasNext` |
| `home_viewed` | INFO | 홈 헤더 조회 | `userId`, `stampCount` |

닉네임은 공통 MDC에 포함된다. 편지 본문은 기록하지 않는다.

## 8. AI 피드백 이벤트

### 처리 시작과 완료

| 이벤트 | 레벨 | 설명 |
| --- | :---: | --- |
| `feedback_job_started` | INFO | 워커가 편지를 선점하고 피드백 작업 시작 |
| `feedback_job_skipped` | INFO | 다른 워커가 선점했거나 처리 가능한 상태가 아니어서 종료 |
| `openai_feedback_requested` | INFO | OpenAI 호출 직전 |
| `openai_feedback_completed` | INFO | 응답 검증과 피드백 저장 완료 |
| `feedback_target_missing` | WARN | 이벤트의 편지가 이미 없어 처리 불가 |

`openai_feedback_completed`에는 다음 결과가 포함된다.

- 실제 응답 모델 ID `model`
- 선택한 우표 `stampName`
- 생성된 팁 수 `tipCount`
- 생성된 교정 구간 수 `segmentCount`
- 호출과 저장에 걸린 시간 `elapsedMs`
- 최종 편지 상태 `status`

### 실패와 재시도

| 이벤트 | 레벨 | 설명 |
| --- | :---: | --- |
| `feedback_retry_scheduled` | WARN | 재시도 가능한 실패로 다음 호출 예약 |
| `feedback_job_awaiting_recovery` | WARN | 일반 재시도 소진 후 보완 복구 대기 |
| `feedback_job_failed` | ERROR | 재시도 불가 또는 모든 복구 예산 소진 |
| `feedback_retry_scheduling_failed` | ERROR | 인메모리 재시도 예약 자체가 실패 |

실패 이벤트에는 다음 원인 필드를 공통으로 기록한다.

| 필드 | 설명 |
| --- | --- |
| `causeType` | 워커가 받은 예외 타입 |
| `causeMessage` | 워커가 받은 실제 예외 메시지 |
| `rootCauseType` | 가장 안쪽 원인 예외 타입 |
| `rootCauseMessage` | 가장 안쪽 원인 예외 메시지 |
| `retryable` | 재시도 가능 여부 |
| `retryCount` | 사용한 일반 재시도 횟수 |
| `recoveryCount` | 사용한 보완 복구 횟수 |

기존의 `cause=IllegalStateException`만으로는 실패 이유를 알 수 없었다. 변경 후에는 다음처럼 정확한 검증 실패 사유가 함께 나온다.

```text
feedback_retry_scheduled userId=7 nickname=jolly letterId=16 status=SUBMITTED retryCount=1 recoveryCount=0 delaySeconds=30 causeType=IllegalStateException causeMessage=OpenAI 학습 팁이 유효하지 않습니다. rootCauseType=IllegalStateException rootCauseMessage=OpenAI 학습 팁이 유효하지 않습니다.
```

## 9. 보완 복구 이벤트

| 이벤트 | 레벨 | 설명 |
| --- | :---: | --- |
| `feedback_job_recovered` | WARN | 멈춘 편지를 다시 `SUBMITTED`로 전환하고 이벤트 발행 |
| `feedback_recovery_exhausted` | ERROR | 보완 복구 횟수까지 소진해 최종 실패 |
| `feedback_recovery_scan_completed` | WARN | 한 번의 스캔에서 발견한 작업 수 요약 |

복구 이벤트에는 `userId`, `nickname`, `letterId`, 이전 상태, `retryCount`, `recoveryCount`가 포함된다.

## 10. 장애 추적 순서

### API 요청 장애

1. 프론트에서 받은 `X-Request-Id`로 검색한다.
2. `business_request_started`에서 사용자와 요청 API를 확인한다.
3. `business_request_rejected` 또는 `unexpected_request_failure`에서 원인을 확인한다.
4. `business_request_completed`에서 최종 상태 코드와 처리 시간을 확인한다.

### AI 피드백 장애

1. 사용자 제보에서 `userId` 또는 편지의 `letterId`를 확인한다.
2. `letter_created`에서 최초 작성 요청을 확인한다.
3. 같은 `letterId`의 `feedback_job_started`와 `openai_feedback_requested`를 찾는다.
4. `feedback_retry_scheduled`의 `causeMessage`와 `rootCauseMessage`를 확인한다.
5. `retryCount`, `recoveryCount`, `delaySeconds`로 다음 실행 시점을 판단한다.
6. `openai_feedback_completed`, `feedback_job_awaiting_recovery`, `feedback_job_failed` 중 마지막 이벤트로 최종 결과를 확인한다.

## 11. 예시: 재시도 후 성공

```text
business_request_started method=POST path=/api/v1/letters operation=LetterController.createLetter clientIp=203.0.113.10
letter_created userId=7 letterId=16 letterDate=2026-08-30 timeZone=Asia/Seoul contentLength=498 status=SUBMITTED
business_request_completed method=POST path=/api/v1/letters status=201 elapsedMs=64 exception=none
feedback_job_started userId=7 nickname=jolly letterId=16 attempt=1 retryCount=0 recoveryCount=0
openai_feedback_requested userId=7 nickname=jolly letterId=16 contentLength=498 stampCandidateCount=115
feedback_retry_scheduled userId=7 nickname=jolly letterId=16 status=SUBMITTED retryCount=1 recoveryCount=0 delaySeconds=30 causeType=IllegalStateException causeMessage=OpenAI 학습 팁이 유효하지 않습니다. rootCauseType=IllegalStateException rootCauseMessage=OpenAI 학습 팁이 유효하지 않습니다.
feedback_job_started userId=7 nickname=jolly letterId=16 attempt=2 retryCount=1 recoveryCount=0
openai_feedback_completed userId=7 nickname=jolly letterId=16 model=gpt-4o-mini-2024-07-18 stampName=꽃_장미 tipCount=3 segmentCount=15 elapsedMs=3100 status=FEEDBACK_COMPLETED
```

이 흐름만으로 사용자, 요청 API, 생성된 편지, 첫 실패 원인, 재시도 횟수, 최종 성공 결과를 연결해 확인할 수 있다.
